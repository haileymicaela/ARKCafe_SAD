# ARKCafe NCR — Integration Testing (Postman)

Adds **integration testing** alongside the existing E2E collection. Nothing was deleted.

Files:
- `ARKCafe-Integration.postman_collection.json` — 55 requests, 6 chained flows
  (generated by `gen_integration.py` — run it once, then you may delete the script)
- Reuses the same environment file as E2E: `ARKCafe-E2E.postman_environment.json`
  ("ARKCafe - Local Dev" — `baseUrl` + admin/staff credentials)

## What integration testing means here (vs E2E)

- **E2E** (you already have it) = one *journey* per role, start to finish.
- **Integration** = testing that *features work together*: login hands a session to every
  later request, CSRF tokens survive across requests, admin CRUD chains hand IDs from
  create → edit → delete, and the staff NCR flow hands the new NCR's ID through status
  changes, edits, search and export.

## What to do next

1. Generate the collection (one command):
   ```powershell
   cd C:\Users\mycha\ARKCafe_SAD
   python postman\gen_integration.py
   ```
   Expected output: `written: ...\postman\ARKCafe-Integration.postman_collection.json`
2. Keep the dev server running (`python manage.py runserver`).
3. Postman → **Import** → `ARKCafe-Integration.postman_collection.json`.
4. Make sure environment **ARKCafe - Local Dev** is selected (same one as E2E — check
   the eye icon: `baseUrl` = http://127.0.0.1:8000 and real credentials are set).
5. Run the folders **in order** (right-click each → *Run folder*):
   1. Admin session & dashboards
   2. Projects CRUD chain
   3. Departments CRUD chain
   4. Logout & session invalidation
   5. Staff NCR lifecycle
   6. Authorization & negative cases
   Or run the whole collection once — the order above is built in.

Folders 1 and 5 start with **0a. GET /login/** and **0b. POST /logout/** so they are safe to run on
their own: the login view has `redirect_authenticated_user = True`, so `GET /login/` returns 302
whenever a session from an earlier run is still alive. Requests that need a captured ID
(`{{projectId}}`, `{{departmentId}}`, `{{ncrId}}`, `{{ncrRef}}`) skip themselves if that ID is missing.

## What to look out for

**Healthy run = every step green.** When a step fails, the failing assertion + the Django
console tell you which link in the chain broke:

| Failing assertion | Meaning / what to check |
|---|---|
| `Sent to admin dashboard` | admin credentials wrong or role isn't `admin` |
| `sessionid cookie issued` | login failed server-side — check Django console |
| `Add project redirects (302)` | POST rejected: CSRF header lost, or duplicate `project_code` from an earlier run (codes are timestamp-unique, so this shouldn't happen) |
| `Project row found (matched by code)` | create succeeded but the list doesn't show a row with this run's unique code — search or list view broke |
| `Edit redirects` → `Edited name is visible` | persistence problem: edit saved but list shows old data |
| `Project no longer listed` | delete didn't work, or the project is protected by linked NCRs (PROTECT relation) — the Django console will show the message |
| `Session invalidated: not served (302)` / `Redirected to login` | logout didn't clear the session |
| `Seed data found (project + department)` | DB has no project/department — run the seed script from E2E-README |
| `Redirects to the new NCR detail` | NCR form rejected — check required fields / seed data |
| `Resolution-type error shown` | a "positive" test: resolving WITHOUT a type must fail validation — if the NCR got resolved, the guard is broken |
| `Status badge is In Progress / Resolved / back to Open` | status transition logic (`ALLOWED_TRANSITIONS`) broke (asserted on this NCR's own status badge, next to its reference) |
| `Status unchanged: badge still Open` | a "positive" guard: after the invalid resolve attempt the NCR must still be Open — if it isn't, the validation guard is broken |
| `Sent back to the same NCR detail` | POST returned 302 but to an unexpected URL — usually a failed validation redirecting back to the form |
| `Response is an xlsx file` / `PK zip signature` | export view broke, returned an empty body, or you hit the wrong URL (must be `/staff/export/`) |
| `Invalid export type rejected (400)` | the 400 guard for bad `export_type` is missing |
| `No session issued` / `Error message shown` (folder 6) | a wrong password must re-render the login form with no session |
| `Not served anonymously (302)` | an anonymous visitor reaching a protected page |
| `Admin page not served to staff` / `Staff page not served to admin` | role isolation broke |
| `Denied (403 from project_views or 302 from core.decorators)` | `administration/project_views.py` has its own `admin_required` that raises 403, while `core.decorators.admin_required` redirects (302). Both are “denied” — this test accepts either, but not a 200 |
| `Select an NCR to export` / `Select at least one column` | the PDF/Excel validation guards are missing |

**Other things to watch:**

- The Django console during the run: a `500` there = real server bug; the failing Postman
  step right before it points at the endpoint.
- The staff NCR chain **leaves one NCR per run** (`Integration NCR <timestamp> - EDITED`,
  reopened to Open at the end). That's intentional — there's no NCR delete endpoint yet.
- The Projects/Departments chains clean up after themselves, so re-running the collection
  is safe; timestamps in codes/names prevent collisions.
- Folder 4 invalidates the session on purpose — don't re-run folder 5 without folder 1–4
  unless you know the cookie jar state; folder 5 logs in as staff itself, so it's fine.
- If you change any URL in Postman, keep the trailing slash — Django POSTs 500 without it.
